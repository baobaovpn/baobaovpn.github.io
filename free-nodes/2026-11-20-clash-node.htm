Clash 应用分流实战：从配置逻辑到规则落地的深度指南

一、为什么"指定应用"是 Clash 真正好用的分水岭

很多人第一次接触 Clash，是被它"能科学上网"这件事吸引的。但真正让 Clash 从"能用"变成"好用"的，并不是节点本身，而是它那套高度灵活的规则系统。尤其是在移动端和桌面端同时使用的场景下，"按应用分流"几乎是每个进阶用户都会遇到的需求。

举个很典型的例子：你希望浏览器、Telegram、YouTube 走代理，但微信、支付宝、银行 App、外卖软件必须走直连。原因很简单——有些应用一旦走代理，要么登录异常，要么风控触发，要么支付失败。这个时候，如果你还在用"全局代理"或者"全局直连"，体验就会非常割裂。

Clash 的 PROCESS-NAME 规则，正是为解决这个问题而生的。它允许你按进程名（在 Android 上通常对应包名）来匹配流量，从而实现"这个应用走代理，那个应用走直连"的精细控制。这篇文章不会只给你一段配置就结束，而是从概念、原理、操作、验证到常见坑，完整讲清楚"Clash 指定应用"这件事。

二、先理解 Clash 的规则匹配逻辑

在动手改配置之前，有必要先弄清楚 Clash 是怎么处理一条网络请求的。

Clash 收到一个请求后，会按照配置文件 rules: 部分从上到下逐条匹配。一旦某条规则命中，就会执行对应的策略（比如 Proxy、DIRECT、REJECT，或者某个策略组名），并且不再继续往下匹配。如果所有规则都没命中，就会执行最后的 FINAL 规则。

这意味着两件事：

第一，规则顺序非常重要。如果你把 FINAL,DIRECT 写在最前面，那后面所有规则都不会生效。
第二，越具体的规则应该越靠前。比如针对某个应用的规则，通常要放在通用域名规则之前，否则可能被提前拦截。

Clash 常见的规则类型包括：

  • DOMAIN：精确匹配某个域名
  • DOMAIN-SUFFIX：匹配域名后缀，比如 example.com
  • DOMAIN-KEYWORD：匹配域名关键字
  • IP-CIDR：匹配 IP 段
  • GEOIP：按国家/地区匹配
  • PROCESS-NAME：按进程名或包名匹配
  • MATCH / FINAL：兜底规则

其中，PROCESS-NAME 就是我们实现"指定应用"的核心。

三、准备工作：确认你用的是支持进程规则的 Clash 内核

这里必须先说一个容易被忽略的事实：不是所有 Clash 客户端都完整支持 PROCESS-NAME。

Clash 原版内核在 Windows、macOS、Linux 上对进程匹配支持较好，但在 Android 上，由于系统权限限制，进程名匹配的实现方式因客户端而异。常见的 Android 客户端如 Clash for Android、Clash Meta for Android（现在多称 Mihomo）、Surfboard 等，对包名匹配的支持程度不同。

所以第一步是确认：

  1. 你使用的 Clash 客户端是否基于 Mihomo（Clash Meta）或较新的内核；
  2. 你的系统是否允许 Clash 读取应用进程信息；
  3. 你的配置文件是否启用了对应的规则解析。

如果是 Android，通常还需要授予 Clash "读取应用列表"或类似权限，否则 PROCESS-NAME 可能无法正确识别。

四、找到应用的包名或进程名

这是整个流程中最关键、也最容易出错的一步。

Android 平台

Android 上，PROCESS-NAME 通常填写的是应用的包名，例如：

  • 微信：com.tencent.mm
  • QQ：com.tencent.mobileqq
  • Telegram：org.telegram.messenger
  • Chrome：com.android.chrome
  • YouTube：com.google.android.youtube

获取包名的方法有几种：

  1. 在系统设置 → 应用管理 → 找到该应用 → 查看应用信息，部分系统会显示包名；
  2. 使用第三方工具，如"包名查看器""App Inspector"等；
  3. 通过 ADB 命令：adb shell pm list packages；
  4. 在 Google Play 网页版链接中查看 id= 后面的部分。

Windows 平台

Windows 上填写的是可执行文件名，例如：

  • Chrome：chrome.exe
  • Edge：msedge.exe
  • Telegram：Telegram.exe
  • Steam：steam.exe

注意大小写通常不敏感，但建议按实际进程名填写。

macOS 平台

macOS 上一般填写应用进程名，例如 Google Chrome、Telegram。部分客户端支持按 Bundle ID 匹配，具体要看内核实现。

五、修改配置文件：从规则到策略组

假设你已经找到了目标应用的包名，接下来就是编辑 Clash 的配置文件。通常文件名为 config.yaml，位置取决于客户端：

  • Windows：多在 Clash 安装目录或 %USERPROFILE%\.config\clash
  • macOS：~/.config/clash 或客户端指定目录
  • Android：通常在应用私有目录，或通过客户端内置编辑器修改

基础写法

在 rules: 部分添加：

yaml rules: - PROCESS-NAME,com.tencent.mm,DIRECT - PROCESS-NAME,org.telegram.messenger,Proxy - PROCESS-NAME,com.google.android.youtube,Proxy - DOMAIN-SUFFIX,example.com,Proxy - MATCH,DIRECT

这段配置的含义是：

  • 微信走直连；
  • Telegram 走代理；
  • YouTube 走代理；
  • example.com 走代理；
  • 其他所有流量走直连。

进阶写法：指定到策略组

实际使用中，我们很少直接写 Proxy，而是写到某个策略组，比如 🚀 节点选择、🌍 国外媒体、🎯 全球直连。例如：

yaml rules: - PROCESS-NAME,com.tencent.mm,🎯 全球直连 - PROCESS-NAME,org.telegram.messenger,🚀 节点选择 - PROCESS-NAME,com.google.android.youtube,🌍 国外媒体 - MATCH,🐟 漏网之鱼

这样做的好处是，你可以在策略组里随时切换节点，而不需要改规则。

多条规则与优先级

如果你希望某个应用先按域名分流，再按进程兜底，可以这样写：

yaml rules: - DOMAIN-SUFFIX,qq.com,🎯 全球直连 - PROCESS-NAME,com.tencent.mobileqq,🎯 全球直连 - PROCESS-NAME,com.tencent.mm,🎯 全球直连 - PROCESS-NAME,org.telegram.messenger,🚀 节点选择 - MATCH,🐟 漏网之鱼

这里需要注意的是，PROCESS-NAME 规则在不同客户端上的匹配时机可能略有差异。有些客户端是在连接建立时匹配，有些是在 DNS 解析后匹配。因此，如果发现某个应用没有被正确分流，可以尝试调整规则顺序，或者结合 DOMAIN 规则一起使用。

六、保存、重载与验证

修改完配置文件后，需要让 Clash 重新加载配置。大多数客户端支持：

  • 点击"重载配置"；
  • 重启 Clash 服务；
  • 在 Android 上切换一次代理开关。

验证是否生效，可以通过以下方式：

  1. 查看 Clash 日志：很多客户端提供实时日志，能看到每条请求命中了哪条规则；
  2. 使用连接面板：Clash 的 Connections 页面会显示每个连接的进程名、目标和命中规则；
  3. 用流量监控工具：观察目标应用是否走了代理；
  4. 实际测试：比如打开 Telegram 看是否正常，打开微信支付看是否正常。

如果发现规则没生效，优先检查：

  • 包名是否写错；
  • 规则是否被前面的规则拦截；
  • 客户端是否支持 PROCESS-NAME；
  • 是否授予了读取应用列表的权限；
  • 配置文件是否真的被加载。

七、常见问题与避坑指南

1. 为什么写了 PROCESS-NAME 还是没效果？

最常见的原因是客户端不支持，或者权限不足。Android 上尤其明显。其次是包名写错，比如把 com.tencent.mm 写成 com.tencent.weixin。

2. 一个应用有多个进程怎么办？

有些应用会启动多个进程，比如推送进程、后台服务进程。这时可能需要为多个进程名分别写规则，或者使用通配符（部分内核支持 PROCESS-NAME 的前缀匹配）。

3. 规则顺序导致误杀

如果你把 MATCH,DIRECT 写得太靠前，后面所有规则都不会执行。一定要把 MATCH 或 FINAL 放在最后。

4. 代理组名称写错

策略组名称必须和 proxy-groups: 中定义的完全一致，包括 emoji。少一个空格都可能导致规则失效。

5. 更新订阅后规则被覆盖

如果你使用的是订阅配置，直接修改本地文件可能在更新后被覆盖。建议使用"覆写"或"规则附加"功能，或者使用支持规则合并的客户端。

八、点评：Clash 指定应用的价值与边界

Clash 的 PROCESS-NAME 规则，表面上看只是一个"按应用分流"的功能，但它背后体现的是一种精细化网络治理的思路。它让用户不再被动接受"全局代理"或"全局直连"的二选一，而是可以根据应用的性质、安全需求、地域限制，做出更合理的决策。

从体验角度看，这种精细化带来的提升是巨大的。微信、支付宝、银行类应用走直连，避免了风控和登录异常；Telegram、YouTube、GitHub 走代理，保证了访问速度和稳定性；国内视频应用走直连，节省了代理流量。这种"各走各道"的配置，才是 Clash 真正强大的地方。

但也要看到它的边界。PROCESS-NAME 并不是万能的。它依赖于客户端和系统的支持，在 Android 上尤其受权限限制；它也无法解决应用内部不同请求需要不同策略的问题——那需要更细的域名规则或脚本能力。因此，把 PROCESS-NAME 当作整个规则体系中的一环，而不是唯一手段，才是更成熟的使用方式。

更重要的是，配置 Clash 的过程本身，其实是一次对自身网络行为的梳理。你会开始思考：哪些流量是敏感的？哪些是必须直连的？哪些是可以走代理的？这种思考，远比复制一份"万能配置"更有价值。

九、总结

在 Clash 中指定应用，核心就是三步：找到包名或进程名，写好 PROCESS-NAME 规则，放到正确的位置并验证。它不复杂，但细节很多。只要理解了 Clash 的规则匹配逻辑，掌握了包名获取方法，注意规则顺序和策略组名称，就能实现非常灵活的应用分流。

对于追求网络体验的人来说，这不仅仅是技术操作，更是一种对自己网络环境的主动管理。希望这篇指南能帮你把 Clash 用得更顺手，也让你的每一次连接都更符合自己的预期。

支持。Matsuri 会自动测试节点延迟并按结果排序。用户可快速选择延迟最低或速度最快的节点，提高网络访问速度，尤其适合游戏或视频场景。

Clash 会周期性检测节点延迟和丢包率，根据测试结果自动选择最优节点。结合策略组和分流规则，用户可体验更快的网页加载、视频播放和游戏连接速度，提高整体网络效率。
Quantumult X 中自定义脚本导致规则异常，该如何恢复？
先停用或删除最近添加的自定义脚本，重启应用并观察网络行为是否恢复。若无法恢复，备份并重置配置为默认，然后逐个添加脚本以定位导致异常的具体脚本并修复。
Mihomo 的日志功能如何开启？
Mihomo 的日志默认关闭以节省性能。若需调试，可在配置文件中启用 `log-level: debug` 参数，日志将输出详细连接信息与错误提示，便于排查问题。
Sing-box 的策略组如何实现按域名分流？
Sing-box 支持根据域名规则匹配流量，将不同网站或应用流量分配到指定节点。结合策略组自动切换低延迟节点，可优化访问速度，保证网络稳定性和流畅体验。
Mellow TUN 模式对系统全局流量的作用是什么？
TUN 模式拦截系统 IP 层的所有流量，实现全局代理效果。相比 SOCKS5 只作用于特定应用，TUN 能覆盖游戏、视频和浏览器流量，保证全系统科学上网体验稳定高效。
